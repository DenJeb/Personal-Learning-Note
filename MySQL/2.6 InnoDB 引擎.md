# 2.6 InnoDB 引擎

[← 返回目录](<MySQL.md>)

## 2.6.1 逻辑存储结构

InnoDB 的逻辑存储结构从大到小依次为：**表空间 → 段 → 区 → 页 → 行**。

| 层级   | 说明                                                                 |
| ------ | -------------------------------------------------------------------- |
| 表空间 | 最高层，逻辑存储空间，一个 MySQL 实例可以有多个表空间                 |
| 段     | 表空间由段组成，分为数据段、索引段、回滚段等                         |
| 区     | 每个区 1MB，包含 64 个页（页大小 16KB）                              |
| 页     | InnoDB 磁盘管理的最小单位，默认 16KB                                 |
| 行     | 数据按行存储，每行包含隐藏字段 `DB_TRX_ID`、`DB_ROLL_PTR`、`DB_ROW_ID` |

## 2.6.2 架构

**内存结构**

| 组件                  | 作用                                       |
| --------------------- | ------------------------------------------ |
| Buffer Pool           | 缓冲池，缓存数据页和索引页，减少磁盘 IO     |
| Change Buffer         | 写缓冲，缓存非唯一二级索引的写操作          |
| Adaptive Hash Index   | 自适应哈希索引，根据访问频率自动建立        |
| Log Buffer            | 日志缓冲区，缓存 redo log                   |

**磁盘结构**

| 组件                         | 说明                                     |
| ---------------------------- | ---------------------------------------- |
| System Tablespace            | 系统表空间（`ibdata1`）                  |
| File-Per-Table Tablespaces   | 独立表空间（`xxx.ibd`），默认开启        |
| General Tablespaces          | 通用表空间                               |
| Undo Tablespaces             | 回滚表空间，存储 undo log                |
| Temporary Tablespaces        | 临时表空间                               |
| Doublewrite Buffer Files     | 双写缓冲文件，保证数据页写入的可靠性     |
| Redo Log                     | 重做日志                                 |

**后台线程**

| 线程                 | 作用                                   |
| -------------------- | -------------------------------------- |
| Master Thread        | 核心后台线程，负责调度其他线程         |
| IO Thread            | 处理 IO 请求                           |
| Purge Thread         | 回收已提交事务的 undo log              |
| Page Cleaner Thread  | 刷新脏页到磁盘                         |

## 2.6.3 事务原理

**redo log**

> **重做日志**：记录事务提交时数据页的物理修改（页号、偏移量、修改内容），用于崩溃恢复，保证事务的**持久性**。

- 采用 WAL（Write-Ahead Logging）：先写日志，再异步刷新脏页
- 即使脏页尚未刷盘，只要 redo log 落盘，崩溃后也能恢复数据

**undo log**

> **回滚日志**：记录数据的逻辑修改（反向操作），用于事务回滚，保证事务的**原子性**。

- 回滚时执行 undo log 中的反向操作（如插入对应删除、更新对应改回）
- 同时 undo log 也是 MVCC 版本链的基础

## 2.6.4 MVCC

> **MVCC（Multi-Version Concurrency Control，多版本并发控制）**：通过维护数据的多个版本，让读写操作互不阻塞，提高并发性能。

**当前读与快照读**

| 类型   | 说明                                                   |
| ------ | ------------------------------------------------------ |
| 当前读 | 读取最新版本并加锁，如 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` |
| 快照读 | 读取可见的历史版本，不加锁，如普通 `SELECT`            |

**隐藏字段**

| 字段        | 说明                                             |
| ----------- | ------------------------------------------------ |
| DB_TRX_ID   | 最近一次修改该行记录的事务 ID                    |
| DB_ROLL_PTR | 回滚指针，指向 undo log 中的上一个版本           |
| DB_ROW_ID   | 隐藏主键（表中没有主键时自动生成）               |

**ReadView**

ReadView 是快照读时生成的一致性视图，包含：

| 字段          | 说明                                   |
| ------------- | -------------------------------------- |
| m_ids         | 生成 ReadView 时所有活跃事务的 ID 列表 |
| min_trx_id    | 活跃事务中最小的事务 ID                |
| max_trx_id    | 下一个将要分配的事务 ID                |
| creator_trx_id| 生成该 ReadView 的事务 ID              |

版本可见性判断（简化）：

1. 版本事务 ID = `creator_trx_id`：自己修改的，可见
2. 版本事务 ID < `min_trx_id`：ReadView 创建前已提交，可见
3. 版本事务 ID >= `max_trx_id`：ReadView 创建后才开启，不可见
4. 否则，若事务 ID 在 `m_ids` 中（仍活跃）不可见，不在则可见

**RC 与 RR 的区别**

| 隔离级别        | ReadView 生成时机                               | 结果                     |
| --------------- | ----------------------------------------------- | ------------------------ |
| READ COMMITTED  | 每次快照读都生成新的 ReadView                   | 能读到其他事务已提交的数据（不可重复读） |
| REPEATABLE READ | 只在第一次快照读时生成，之后复用                | 同一事务内多次读取结果一致 |
